# Mailsink architecture

Mailsink captures and emulates transactional email. It never delivers to the outside world.
Two usages share one engine:

- **E2E / CI**: ephemeral workspaces provisioned per test worker through the Admin API,
  idle TTL, chaos overrides, assertions through the Capture API or MCP.
- **Staging / QA**: persistent workspaces with drop-in Resend, Brevo and SMTP endpoints,
  plus a web UI to inspect rendered emails, SMTP transcripts, API calls and webhooks.

## Key architecture decisions

Decisions marked *owner* were taken or approved by the product owner. Decisions marked
*proposition* are the architect's or an agent's defaults, open to veto, each tracked in an
issue.

| # | Decision | Status |
|---|---|---|
| D1 | **Every HTTP surface lives inside the TanStack Start app** (server routes): Admin, native `/v1`, Resend, Brevo, Capture, SSE, MCP. No separate Fastify/Elysia server. | owner |
| D2 | Issues/PRs/commits in French; code, README and docs in English. Public repo, MIT. | owner |
| D3 | **One Node process**: an idempotent runtime (migrations, SMTP listener, workers) runs next to the HTTP handler. Single-instance by design; horizontal scaling is out of scope for v1. Boot mechanism (spike #9): the custom server entry `src/server.ts` alone is not enough, because the Nitro build imports it lazily at the first HTTP request (SMTP would stay closed until then). A Nitro plugin (`src/runtime/nitro-plugin.ts`, registered in `nitro.config.ts`) boots the runtime at process start and stops it on Nitro's `close` hook; `src/server.ts` only makes requests wait for the runtime. A `globalThis` slot keeps one runtime across Vite HMR and across the two production bundles. In `vite dev`, editing runtime code restarts the runtime by itself (`runtime/restart.ts`: stop, then boot from the new code, restarts within 500 ms coalesced, requests meanwhile wait for the new runtime; D63). In `vite dev` the runtime lives in Nitro's worker thread where signals never arrive, so the `close` hook is the stop path there. Shutdown in production (#55): srvx traps SIGTERM/SIGINT, drains in-flight HTTP (`SERVER_SHUTDOWN_TIMEOUT`, 5 s) then fires the `close` hook, which stops SMTP, the worker and the database; the Mailsink signal handler waits for that stop, then exits 0 (a second signal or a 17 s overrun exits 1). With `CI` or `TEST` set, srvx skips its drain and the handler stops the runtime itself. | owner (boot mechanism approved 22/11, #56; dev restart 23/11, #72) |
| D4 | Domain logic lives in framework-agnostic packages (`core`, `db`, `contracts`); server routes and server functions are thin adapters. The SMTP server and MCP call the same services. | owner |
